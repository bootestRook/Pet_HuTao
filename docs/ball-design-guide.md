# 小球角色设计与实现指南

本指南用于根据人物外貌、性格、经历、爱好和台词，设计可辨认、可理解、可实现的小球角色。后续新增小球和修改现有角色时，沿用这里的设计流程、特效规范和交付模板。

核心原则是：**人设决定主题，性格形成机制，外貌提供辨识度，战斗反馈跟随对应的小球。** 通用规则与角色专属数值分别维护；用户最新明确要求优先于已有方案和本指南的默认做法。

## 设计流程

1. **提炼资料。** 列出已知事实、核心性格、辨识特征和有价值的反差；保留会影响设计的未知项。
2. **先出方案。** 默认先给出主题、外形、一个或多个固定效果、动效、台词和首轮数值。用户已明确要求制作或按某版实施时，直接进入实现，不重复索取确认。
3. **落实最终版本。** 用户修订某条规则后，统一更新机制、描述、画面、日志和验证；删除被替代的表现与逻辑。
4. **完成最小可玩版本。** 先打通角色选择、服务端结算、同步和画面反馈，再逐项增加能力。
5. **检查结果。** 核实机制边界、动态跟随、桌面与手机布局以及多人同步，分别记录验证范围。

纯方案或审阅请求只输出对应成果；实现请求包含必要的结果检查和问题修复。

## 人设转译

| 输入资料 | 优先转译为 | 使用要求 |
| --- | --- | --- |
| 眼镜、发型、服饰等外貌 | 脸部、轮廓和配饰 | 缩小后仍能辨认 |
| 核心性格和习惯 | 固定效果的触发方式、收益与代价 | 能解释效果为什么属于这个人 |
| 经历、爱好和职业 | 配色、图案、动作、台词或能力细节 | 挑选有辨识度的内容，不必每条都做成能力 |
| 自述与实际表现的反差 | 得意、失败和翻车表现 | 保留反差，不把吹嘘当成真实能力 |
| 明确指定的数值或规则 | 角色效果的具体条款 | 按最终要求落实，不私自替换 |

- 优先确定一个核心主题和两个主要辨识特征，其余资料作为辅助细节。
- 身高、体重不直接换算成生命、伤害或移动速度。单位未注明时，不擅自补成事实或据此判断胖瘦。
- “自诩教练”不等于已经确认专业能力；“自称很强”不等于战斗属性必须很强。
- 游戏经历和爱好可以成为角色梗，但不能仅凭游戏数量判断现实职业能力。
- 只澄清无法合理推断、且会实质改变方案的信息；可选细节不成为阻塞条件。

## 外形规范

- 保持圆球主体和清楚的碰撞边界；装饰、光晕、骰子和巴掌不额外扩大判定范围。
- 用眼镜、眼神、嘴角、头带等少量元素建立识别，不把完整人体硬塞进球体。
- 主体色保持稳定，辅助色服务于角色主题和战斗状态；状态还应有图形、点数或文字提示。
- 在实际对战尺寸下检查外形。当前小球半径为 32 个逻辑单位，细小文字和大量配件容易失去辨识度。
- 生命数字、玩家标记和表情应各自可读；同角色对战时，用 P1/P2 与边框区分玩家。

当前基础起点为生命 100、碰撞伤害 10、速度 300 单位/秒、半径 32，逻辑战场为 420 × 420。新角色优先沿用这些基础值，以固定效果形成差异；这些数值可以随明确的玩法要求调整。

界面详情仅展示基础数值与简短效果；每个固定效果独立成段，不用“【】”包裹名称。技能名使用金色流光，减少动态模式保留金色而关闭动画；伤害、治疗、时间、概率和次数使用语义化富文本突出。人设、特效过程与完整结算细则保留在角色文档中，不堆进选装说明。道具说明同样只保留简短效果和关键数值。

## 固定效果定义

每个小球可以有一个或多个固定效果。默认先完成一个核心效果；有明确的人设联系时增加其他效果，不为凑数量而叠加能力。固定效果随小球自动生效，不占当前保留的道具、技能或特性槽位。

每个效果必须能回答以下问题：

| 条目 | 必须说明的内容 |
| --- | --- |
| 名称与人设来源 | 表现哪种性格、习惯或反差 |
| 触发条件 | 按时间、碰撞、血量或其他明确事件触发，何时首次检查 |
| 作用对象 | 自身、受击者或其他明确目标，是否受距离限制 |
| 数值与限制 | 伤害、回血、阈值、上限、次数、重置条件与可否致死 |
| 动效与结算 | 动效持续多久，开始还是落定时结算，期间战斗是否继续 |
| 关联与结束 | 是否算球体碰撞、能否触发其他能力，死亡与战斗结束时如何处理 |
| 随机与统计 | 各结果概率、伤害及治疗如何计入统计 |

随机效果需要列明概率，并可用单次期望检查数值方向。期望必须说明是否忽略回血溢出、提前死亡和其他效果；不能单凭期望宣布角色已经平衡。

服务端决定点数、伤害、治疗和胜负。客户端的翻滚、粒子和飘字只展示结果；本地装饰动画不能重新决定随机结果。治疗统计记录实际恢复量，伤害统计记录实际造成的伤害，避免把溢出治疗或过量伤害计入有效收益。

## 战斗特效与飘字规范

角色能力默认以场内特效表现，禁止用场中央的角色技能卡片或骰子面板代替。战斗持续进行，特效应短暂、清楚，留出观察小球和生命变化的空间。

| 反馈 | 跟随对象 |
| --- | --- |
| 随身骰子、蓄力和自身状态 | 发动能力的小球 |
| 巴掌与受击表现 | 被打的小球 |
| 普通伤害和远程伤害飘字 | 受到伤害的小球 |
| 自损飘字 | 自损的小球 |
| 回血飘字和回复光效 | 实际接受治疗的小球 |
| 忆往昔照片光框 | 发动忆往昔的小球 |
| 随机台词 | 说话的小球或其随身特效旁 |

实现时按目标身份查找小球，使用与球体相同的**每帧插值位置**作为锚点。只在触发时取一次坐标、或把特效留在事件发生处，都不满足跟随要求。锚点之上可以叠加挥掌、上浮、旋转等局部动作；小球移动、反弹后，特效仍应贴着对应对象。

- 飘字保留浮动、淡出和多条错层，但这些偏移始终叠加在移动锚点上。
- 靠近边缘时调整摆放或限制文字位置，保持点数、数值和台词可读。
- 同角色对战时，各自显示自己的骰子与台词；伤害和治疗不能串到另一名玩家身上。
- 减少动态模式可以去掉旋转、抖动和装饰粒子，但必须保留点数、结果与正常的小球运动。
- 已结算的致命结果可以短暂保留，随后消失；未落定的能力不能在战斗结束后继续结算。
- 若以后明确设计定点区域或独立投射物，应单独写清其位置与轨迹规则，不把这种行为当作角色跟随特效的默认实现。

## 胡涛最终示例

### 人设与外形

胡涛的主题为“嘴强王者、怀旧教练”。黑框眼镜、青蓝运动头带和歪嘴笑构成主要外形，夸张金冠表现吹嘘王者实力的反差，三枚小饰钉对应一年三款 Steam 游戏的彩蛋。翻车时眼镜滑落、金冠歪斜，忆往昔用暖金照片框表现。

人设依据包括自诩健身教练、喜欢上嘴脸和忆往昔、喜欢鸣潮与二次元，以及吹嘘王者荣耀很厉害却打不过低分匹配局。原始资料中的“身高172、体重120”不用于推导战斗强度，也不据未注明的单位追加体型结论。

基础生命 100、碰撞伤害 14、速度 330 单位/秒、半径 32。普通碰撞承担主要输出，较快速度形成活跃的对战节奏，保留骰子翻车与一次性回血的反差；属性补偿依据实际技能表现，不把自诩教练或吹嘘实力视为真实战斗能力。

### 上嘴脸

每 10 秒投掷一颗独立六面骰子。骰子跟随自身，在身旁翻滚 0.8 秒后结算，期间战斗继续。

| 点数 | 效果 | 概率 |
| --- | --- | --- |
| 1 | 自身恢复 12 点生命，不超过上限 | 1/6 |
| 6 | 无视距离扇对方一巴掌，造成 8 点伤害 | 1/6 |
| 2～5 | 扣除自身 4 点生命，可以致死 | 4/6 |

巴掌不改变物理运动，不增加球体碰撞次数，也不直接触发碰撞后的能力。骰子落定后短暂保留点数、光效和随机台词；巴掌跟随受击者，数值反馈跟随实际受影响的小球。

忽略上限、提前死亡和其他效果时，单次投掷的自身生命期望变化为 `12 × 1/6 − 4 × 4/6 = −2/3`，对手为 `−8 × 1/6 = −4/3`。整体强度还受碰撞、一次性治疗和对手类型影响。

### 忆往昔

双方球体碰撞伤害结算后，首次满足“胡涛仍存活且生命值 ≤40”时，恢复 25 点生命。每局一次，不超过生命上限，不能复活。

骰子自损和远程巴掌不直接触发忆往昔。若此前已经因此降至阈值以下，后续球体碰撞结算后仍存活且符合条件，仍会触发。

### 结算与台词

同一模拟步先处理球体碰撞；若已结束战斗，就取消尚未落定的骰子。战斗仍进行时，同步到期的骰子先处理回血与自损，再处理双方巴掌，最后判断胜负，允许同刻双杀。

每次骰子结果结算时，从以下列表等概率抽取一句，跟随胡涛的骰子显示，并写入战况记录：

- 龙逼
- 666
- 破绷
- 我叼你妈

这些台词属于胡涛，不作为其他角色的默认台词。

## 实现与验收

优先接入已有目录、战斗和渲染流程，保持角色数据、结算和表现分离。替换旧方案时移除失效的路径与样式，不为尚未提出的需求增加兼容层或通用框架。

| 位置 | 维护内容 |
| --- | --- |
| [shared/catalog.ts](../shared/catalog.ts) | 角色入口、基础属性、简介和完整效果说明 |
| [shared/hutao.ts](../shared/hutao.ts) | 胡涛数值、概率分支和台词，作为角色常量的现有示例 |
| [shared/types.ts](../shared/types.ts) | 多人同步所需的角色状态与战斗事件 |
| [server/battle.ts](../server/battle.ts) | 服务端随机、触发、结算、次数、统计与结束逻辑 |
| [client/arena.ts](../client/arena.ts) | 位置插值、特效目标绑定、飘字和生命周期 |
| [client/hutao-art.ts](../client/hutao-art.ts) 和 [client/hutao-dice.ts](../client/hutao-dice.ts) | 现有角色形象、巴掌和随身骰子表现 |

交付前逐项检查：

- 方案、目录描述、服务端数值、战况日志和画面使用同一版规则。
- 随机分支、触发周期、回血上限、自损致死、一次性次数及结算顺序正确。
- 双方伤害与治疗同时到期时，胜负不因座位或处理顺序产生额外优势。
- 特效在目标移动和插值过程中持续跟随，靠边可读，持续时间结束后消失。
- 同角色、观战、刷新与重连展示同一结果；旧效果不会因重连被重新结算。
- 桌面与手机尺寸、减少动态模式下都能辨认角色和关键反馈。
- 记录实际完成的逻辑检查、生产构建、浏览器检查与真实跨设备检查，不能把手机尺寸截图当作另一台手机实测，也不能把定向检查写成完整验收。

按改动范围运行相关检查；实施改动可使用以下项目命令，浏览器检查需要先启动服务：

```powershell
npm run typecheck
npm test
npm run build
npm run test:e2e
```

胡涛的现有回归入口为 [逻辑测试](../tests/hutao.test.ts)、[骰子与双客户端浏览器检查](../tests/hutao.browser.spec.ts) 和 [巴掌与飘字跟随检查](../tests/effects.browser.spec.ts)。
